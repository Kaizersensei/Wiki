Startup Splashes (Parameter-Driven)

Purpose

The startup splash system provides reusable, parameter-driven splash scenes for the boot sequence. Instead of hardcoding a single logo screen, the engine can play an ordered list of splash presets (company logo, startup notices, platform warnings, etc.) before the loading screen appears.

Core type: DensetsuSplashScreen

DensetsuSplashScreen is a reusable splash node (CanvasLayer-based) with exported parameters controlling:

  • timing (fade-in / hold / fade-out / skip fade-out),
  • visuals (background color/texture, logo texture, tints),
  • text (title, subtitle, skip hint),
  • input skipping (actions, any-input option, minimum delay before skip).

The intent is to create many small preset scenes that all instance the same splash base scene and only override exports.

Bootloader sequencing

  • The bootloader holds an ordered array of splash scenes.
  • It instances each splash scene, calls play(), and awaits its finished signal.
  • After the sequence completes, the bootloader instantiates the loading screen and begins threaded scene loading.

This keeps sequencing policy centralized while keeping splash scenes reusable and self-contained.

Recommended reuse pattern

  1. Keep one reusable splash base scene/type.
  2. Create small preset scenes for each startup message type.
  3. Configure the bootloader splash list for the desired startup sequence.
  4. Avoid copy-pasting splash logic across many scene variants.

Best practices

  • Keep startup splashes lightweight (avoid heavy assets unless explicitly tested).
  • Use short, deterministic durations and fade timings.
  • Enable skipping only after a small minimum delay to prevent accidental instant skips.
  • Use splash scenes for public-safe startup messaging only.

Known risks / caveats

  • If splash scenes pull large assets or expensive scripts, startup may appear frozen before the loading screen.
  • Startup stalls before any splash appears are usually pre-bootloader issues (script parse, imports, preloads, autoloads).
  • Overusing splash complexity defeats the purpose of a fast, deterministic startup path.
