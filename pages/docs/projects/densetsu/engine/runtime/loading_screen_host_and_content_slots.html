Loading Screen Host & Content Slots

Purpose

DensetsuLoadingScreen is a reusable runtime loading host. It combines a configurable overlay UI (status + gauge) with a freeform content slot so one scene can support simple progress bars, animated branding, music/video, slideshows, or interactive loading content.

Design model

  • Content host: ContentRoot receives arbitrary child scenes/nodes.
  • Overlay UI: gauge + labels for progress/status/detail.
  • Threaded loader: requests and polls a target scene asynchronously.
  • Top-level forwarding: root node exposes gauge/panel/label parameters so users do not need to edit child nodes directly.

Content slot usage patterns

The loading screen can host almost any content scene that is safe to run during loading:

  • logo animation or studio splash,
  • music visualizer,
  • video/cut-in presentation,
  • slideshow/tips screen,
  • interactive showcase (e.g., rotating model),
  • mini-scene / lightweight minigame.

Because it is a regular scene host, the loading screen is intentionally not limited to a “UI-only” implementation.

Top-level parameter exposure strategy

The loading screen node exposes configuration at the root level to keep tuning fast and deterministic:

  • Overlay visibility and panel visibility/modulate
  • Panel layout (size, bottom margin, minimum size, style override)
  • Status/detail label visibility and modulate
  • Gauge preview progress and visual settings (colors, textures, smoothing, border, text)
  • Threaded load behavior (auto start, target path, auto switch, minimum visible time)

This avoids inspector hunting in deep child-node hierarchies and makes the scene practical as a reusable engine-level tool.

Threaded loading behavior

  • Loading starts via begin_load_scene(scene_path).
  • The node polls progress and emits signals for start/progress/completion/failure.
  • It can auto-switch to the loaded scene after a minimum visible time.
  • A preview/idle gauge value can be shown when not actively loading.

Practical note: scene switch is still a handoff point, so large target scenes may have a visible transition cost if the final activation is expensive.

What this solves well

  • One loading scene for multiple use cases and themes.
  • Fast iteration without breaking scene internals.
  • Clear separation between boot sequence policy and loading-screen presentation.
  • Runtime-friendly progress UI that can remain lightweight.

What it does not solve

  • Engine startup stalls that happen before the loading scene is instantiated.
  • Heavy content placed into the loading screen itself (the content slot can still cause stalls if overloaded).
  • Project-wide async resource strategy by itself (this is a scene-loading host, not a full streaming framework).

Usage guidelines

  • Keep loading-content scenes lightweight unless they are intentionally designed/tested for heavy startup use.
  • Prefer parameter tuning on the root node over editing child controls.
  • Use the bootloader to set target path and startup sequence policy; keep the loading screen focused on presentation + loading behavior.
