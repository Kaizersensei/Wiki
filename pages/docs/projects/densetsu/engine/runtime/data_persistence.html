The live runtime tree does not expose one unified save system yet. What exists today under the persistence umbrella is a smaller set of concerns: boot configuration through manifest and catalog services, directory-scan fallback for older data consumers, persistent diagnostics logging, and typed in-memory snapshot contracts for runtime state.

Critical Repository Drift

Verified mismatch: the runtime services still default to res://data/runtime/production_runtime_manifest.json and res://data/runtime/production_data_catalog.json, but those files are not present in the current repository snapshot.

Implication: manifest/catalog persistence is real in code and in the rewrite worklog, but the checked-in asset layer for that path is incomplete in this snapshot and should not be documented as fully present.

What Not To Assume

  • Do not treat loading-screen flow or scene reload helpers as save-system behavior.
  • Do not assume the worklog’s manifest/catalog asset files still exist in the current tree just because the service code references them.
  • Do not treat snapshot classes as proof of a completed save-file format; they are current state contracts, not a finished persistence pipeline.
