Bootloader / Loading / Splash Pipeline

Purpose

This pipeline provides a controlled startup flow for the public Densetsu engine: startup splashes, a reusable loading-screen host, and threaded scene loading before handoff to the target map/scene.

Core components

  • DensetsuBootLoader: project entry scene that sequences splashes and loading.
  • DensetsuSplashScreen: parameter-driven splash scene type (logo/info/startup messaging).
  • DensetsuLoadingScreen: loading host scene with overlay UI + content slot + threaded scene request.
  • DensetsuLoadingGauge: configurable smooth progress control used by the loading screen.

Startup sequence (runtime)

  1. Godot starts and loads the configured main_scene (the bootloader scene).
  2. Bootloader resolves the target scene path.
  3. Optional startup splash scenes are played in order.
  4. Bootloader instances the loading screen scene.
  5. Loading screen starts a threaded request for the target scene.
  6. Loading screen reports progress and optionally auto-switches to the loaded scene.

How the bootloader knows what to load

The bootloader resolves the target from a default exported target_scene_path, with optional command-line overrides. Two forms are supported:

  • --scene=res://path/to/scene.tscn
  • --scene res://path/to/scene.tscn

This allows one bootloader scene to serve normal game startup, test launches, and QA/automation scenarios.

Responsibilities and boundaries

  • Sequence startup visuals and scene loading in a predictable order.
  • Centralize startup policy (skip behavior, splash ordering, minimum loading screen time).
  • Keep startup screens reusable and parameter-driven.
  • Do not become a general runtime manager or a heavy content scene itself.

Important limitation: what it cannot hide

The bootloader runs after Godot has already loaded the bootloader scene/script and its dependencies. It cannot hide or solve stalls that happen earlier, such as:

  • script parsing/compilation errors,
  • resource import/remap checks during startup,
  • heavy preload() dependencies inside the bootloader or splash scenes,
  • autoload singleton startup work,
  • editor/project scanning stalls (during preview runs).

When startup appears frozen before any splash or loading UI appears, the stall is usually before the threaded target-scene load stage.

Known failure modes / debugging notes

  • Perceived hang after boot completion may occur before loading begins if a splash or boot dependency is heavy.
  • Verbose boot logging is useful to determine the last startup milestone reached.
  • If a splash scene references large assets, startup may stall before the loading screen appears.
  • For quick isolation, disable splashes or point the bootloader to a small test scene.

Design guidelines

  • Keep bootloader logic small and deterministic.
  • Prefer lazy-loading content through the loading screen instead of heavy startup preloads.
  • Treat splash scenes as lightweight presentation scenes, not content-rich showcase scenes (unless intentionally tested).
