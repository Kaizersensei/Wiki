The runtime rewrite establishes one explicit boot root, one manifest-driven startup path, and one set of autoloaded service boundaries. The old habit of treating whichever map happened to open as the runtime entry point is no longer the intended architecture.

Boot Sequence

  1. project.godot starts res://engine3d/runtime/RuntimeBootstrap.tscn.
  2. RuntimeBootstrap acquires diagnostics, manifest, catalog, and scene-flow services from the autoload layer.
  3. RuntimeManifestService validates startup-critical resources such as startup scene, player scene, loading screen, and catalog paths.
  4. DataCatalogService validates and resolves explicit category-to-resource mappings.
  5. SceneFlowService hands execution to either the production startup scene or the debug scene selector path.

Current Boundaries

  • The runtime manifest and data catalog exist and are active, but catalog scope is still migration-limited rather than fully exhaustive.
  • Some runtime consumers still keep migration fallback behavior around catalog-backed lookup instead of treating the catalog as the only path yet.
  • The debug selector is part of the intended boot surface, not a side-door replacement for runtime startup discipline.
  • Diagnostics and visible failure handling are part of the runtime contract because blank-screen export failures were a real problem during the rewrite.

Validation Surface

  • Runtime smoke scenes live under engine3d/tests/.
  • The worklog treats validation as mandatory, not optional manual spot-checking.
  • Headless acceptance still has environment-specific reliability limits, so some passes rely on rebuilt tester packages and runtime diagnostics instead of pure headless confidence.
