The repo-local design notes clearly reserve a separate save-system layer for playthrough state, but that layer is not implemented as a dedicated runtime service in the live engine3d/runtime tree. The current runtime exposes state contracts and scene-loading flow, not a finished save-slot pipeline.

What Exists Today

Surface Verified state
Runtime state contractsTyped snapshot objects exist for player, combat presentation, inventory presentation, objective, location, calendar, and aggregated world presentation state.
Scene load flowSceneFlowService and DensetsuLoadingScreen handle scene transitions and reloads with a loading screen, not save restoration.
Diagnostics persistenceDiagnosticsService writes user://runtime_diagnostics.log for non-editor sessions.
Save-oriented design notesdocs/db-structure.md and docs/biome-driven maps.md describe separate runtime save data and stable generated IDs as future-facing requirements.

What Is Missing In The Live Runtime Tree

Expected save/load concern Current repository truth
Save autoload or runtime serviceNo SaveService, save-slot manager, or equivalent runtime autoload is present.
Boot-time restore pathRuntimeBootstrap validates manifest/catalog/services and starts scene flow; it does not restore playthrough state from disk.
File-backed gameplay state serializerNo repo-local save-file writer/reader is exposed in engine3d/runtime.
Save/load smoke coverageNo dedicated smoke scene for save-slot serialization or restore flow is present under engine3d/tests/.
Persistent world mutation layerThe runtime snapshot contracts are in-memory read models, not a durable world-state store.

Planned Direction From Design Docs

  • docs/db-structure.md explicitly separates the authoring database from a playthrough save DB or save file.
  • The same design notes place runtime mutations under concepts such as SaveState, RuntimeState, and WorldState, not under the authoring DB.
  • docs/biome-driven maps.md treats deterministic generated IDs as a prerequisite for later save/load reliability in generated worlds.

Documentation Boundary

Do not confuse scene loading with save loading. The current runtime has a documented loading-screen and scene-flow pipeline, but that is not a save restore system.

Do not overstate snapshot contracts. They are useful state boundaries that could support a future save format, but the repo does not yet expose the durable save/load layer those notes imply.
