Actor capabilities describe what an actor can do. They are not actor categories, and they are not runtime state. The authoring database needs this distinction because the same base actor may be player-controllable, dialogue-capable, rideable, combatant, or harvestable without becoming five different actor types.

Core Rule

  • Category answers what the thing fundamentally is.
  • Capability answers what the thing can do.
  • Runtime state answers what the thing is doing right now.
  • Variant answers how this authored form differs from its base record.

Recommended Capability Families

Family Example capabilities Notes
Controlcontrollable_by_player, controllable_by_ai, possessable, commandableDefines control ownership, not narrative role.
Socialdialogue_capable, merchant, trainer, quest_anchor, recruitableUse relations or tags rather than separate actor classes.
Combatcombatant, hostile_default, guard_capable, parry_capable, drops_lootKeep these separate from current aggro or alive/dead state.
Mountingrideable, can_mount, tameable, bond_tracked, rider_slot_providerrideable and can_mount belong to different actors and must not be merged.
Interactionharvestable, cuttable, flammable, can_be_grabbedImportant for active objects, resource nodes, and environmental actors.

Authoring Expectations

Record concern Expected authoring behavior
Base actor recordDefines actor family, default assets, base behavior, and default capability relations.
Variant recordOverrides only the fields or capability deltas that differ from the base actor.
Runtime stateStored outside the authoring catalog as save data, FSM state, or live relationship state.
UI behaviorEditors should support add/remove capability actions, base comparison, validation, and resolved previews.
