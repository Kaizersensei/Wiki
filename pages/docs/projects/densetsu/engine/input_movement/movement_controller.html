The current repo no longer has one simple movement-controller script for the shell path. Movement is a chain: input becomes a command frame, the character motor owns the live shell locomotion when present, and the older movement component remains as a compatibility mirror or fallback executor.

Ownership Chain

Layer Verified owner Current responsibility
Input captureActorInputComponent3DReads project actions, resolves or directly builds a PlayerCommandFrame3D, and publishes it each physics tick.
Live shell movement authorityCharacterMotorModel3DOwns locomotion, gait arbitration, jump and traversal handoff, posture, burst movement, state tags, and animation intent on the shell path.
Compatibility mirrorActorMovementComponent3DMirrors motor state when the motor is active, or runs its own fallback locomotion path when no motor authority is present.
Presentation and consumersAnimation, presentation, combat, inventory, camera, UI, and state-machine componentsRead command frames, movement state, or published actor state tags without needing to own locomotion themselves.

Shell Player Wiring

  • ActorPlayerShell3D.tscn wires the current shell player with Input, CharacterMotor, Movement, Traversal, ShellStateMachine, Presentation, and Camera nodes together under ActorShell3D.
  • That scene layout is the clearest current reference for the movement stack the rewrite is actually validating.
  • The legacy player scene still exists and still matters elsewhere, so this page documents the shell movement chain without pretending it already replaced all legacy runtime locomotion.

What The Motor Owns Now

  • Grounded and airborne locomotion.
  • Walk, run, and sprint separation, including analog walk thresholds and start, stop, landing, and turn variants.
  • Crouch or crouch-move posture behavior, with sneak collapsed into the crouch family in the current runtime vocabulary.
  • Jump, double jump, wall jump, dash, and roll.
  • Camera-relative direction handling plus side-scroller-aware movement when that camera context is active.
  • Actor state-tag publication and motor-owned animation intent for downstream presentation systems.

Why The Old Movement Component Still Exists

  • The rewrite worklog explicitly records that ActorMovementComponent3D had been carrying two responsibilities at once: command-frame capture and locomotion execution.
  • The current split moves command-frame capture into ActorInputComponent3D and live shell authority into CharacterMotorModel3D.
  • ActorMovementComponent3D still matters because other systems already listen to its published command frame or state surface, and because it can still execute locomotion when a shell actor does not have the new motor authority active.

Safe Current Assumptions

  • If a shell actor has an active CharacterMotorModel3D, that motor is the first movement authority and the movement component disables its own physics execution path.
  • If the motor is absent, the movement component still has a real fallback locomotion implementation driven by MovementData3D.
  • Movement tuning remains resource-driven. Walk, run, sprint, air, jump, wall, dash, roll, and posture numbers still come from MovementData3D.

Known Boundaries And Risks

  • The page title is singular, but the implementation is distributed across multiple shell components and one motor model.
  • Legacy actor roots still own movement in older runtime paths, so shell movement documentation should not be read as a universal actor statement.
  • Consumer systems are still being migrated away from older compatibility surfaces, which is why mirrored state tags and bridge components remain in the tree.

Validation

  • engine3d/tests/smoke_actor_player_shell.gd verifies shell movement, command-frame publication, and state synchronization through the player shell path.
  • docs/production_rewrite_worklog.md records the split of input capture away from the movement component and the later promotion of CharacterMotorModel3D into first movement authority.
  • ActorPlayerShell3D.tscn is the concrete scene proof that input, motor, movement mirror, traversal, and presentation are all wired together in the current rewrite path.
