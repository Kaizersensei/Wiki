Documentation standards for the overhaul

  • Every page should declare page type, audience, implementation status, last verified date, and primary code paths at the top.
  • Pages should answer the fast questions first: what this is, when to read it, and what code or content it governs.
  • Design intent, current implementation, and open questions should be visually separated so readers do not confuse aspirational notes with working behavior.
  • Use tables for inputs, outputs, signals, state transitions, data schema fields, dependencies, and file ownership.
  • Use callout boxes for risk, migration notes, unstable behavior, and pending verification.
  • Prefer diagrams, screenshots, scene-tree captures, and flowcharts where they reduce ambiguity; track missing visuals as explicit placeholder items rather than silent TODOs.
  • Link laterally across related pages so a developer can jump from overview to workflow to API/reference without hunting through indexes.

What should not become one-page-per-file docs

  • Individual imported images, models, and raw asset files unless they are canonical examples for a workflow.
  • Every .import file or generated metadata file.
  • Upstream addon internals that have not been locally modified or wrapped.
  • Every backup, broken, temp, or deprecated scene snapshot; document the cleanup policy instead.
  • Every demo asset instance; document the demo scene purpose and setup rules instead.
