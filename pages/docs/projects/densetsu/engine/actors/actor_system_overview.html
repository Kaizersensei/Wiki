The important rule for the current codebase is simple: the shell path is real, but the monolith still matters. Any actor documentation that implies the shell already replaced ActorCharacter3D is wrong for the June 2026 repo state.

Legacy vs Shell

Layer Current verified state Direction
Actor rootActorCharacter3D is still the legacy runtime authority.Shrink ownership over time rather than refactor it all at once.
Player rootActorPlayer3D still extends the legacy path in production.Move toward shell-owned player scenes when compatibility risk is acceptable.
Shell rootActorShell3D and shell scenes for player, NPC, and enemy are present.Become the reusable actor composition base.
ComponentsInput, movement, combat, traversal, animation, camera, inventory, identity, and state-tag components already exist.Turn stable gameplay domains into component-owned or service-owned contracts.
Runtime lookupPlayerActorService bridges runtime reads across legacy and shell actors.Reduce direct scene-tree assumptions elsewhere in runtime code.

What Is Safe To Assume

  • The shell path is not dead scaffolding. It is the migration target and already powers validation scenes and non-legacy actor variants.
  • The monolith is still dangerous to touch because it affects player and NPC runtime behavior broadly.
  • The player service and typed component accessors are part of the strategy for reducing broad runtime-value lookups and scene-owner coupling.

Known Risks

  • ActorCharacter3D.gd remains one of the highest-risk files in the project.
  • Player, camera, combat, and presentation responsibilities are still split across legacy and shell paths in places.
  • Migration progress in the worklog does not mean every production scene already points at the shell path.

Validation

  • The rewrite worklog treats shell scenes and actor smoke passes as proof points for migration slices.
  • engine3d/tests/ includes smoke coverage for runtime bootstrap, runtime player, export-manifest closure, and actor shell initialization.
