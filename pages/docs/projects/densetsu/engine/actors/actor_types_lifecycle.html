The current actor lifecycle is transitional rather than uniform. The repo contains both the legacy monolith path and a real shell/component path, and documentation has to describe where each one is authoritative instead of flattening them into one fictional system.

Current Actor Families

Family Verified root Current role
Legacy base actorActorCharacter3DMonolithic gameplay authority for the older runtime path.
Legacy playerActorPlayer3DProduction player root that still extends ActorCharacter3D while attaching rewrite components at runtime.
Legacy NPCActorNPC3DMonolithic NPC path with budgeting, wander, and animation-driver runtime support.
Legacy animalsAnimalNPC3DAnimal-specialized NPC path layered on top of ActorNPC3D.
Shell base actorActorShell3DComponent-composition root for the rewrite path.
Shell player and humanoidsActorPlayerShell3D.tscn, ActorHumanoidNPCShell3D.tscn, ActorHumanoidEnemyShell3D.tscnValidated migration scenes for player, NPC, and enemy composition.

What Player Runtime Actually Uses

  • ActorPlayer3D.gd still extends ActorCharacter3D.gd. That is the clearest signal that the player monolith has not been fully retired.
  • The same player root now attaches rewrite components and exposes get_actor_components(), get_component_by_script(), and state-tag publication so services can move toward shell-friendly contracts without an all-at-once scene swap.
  • PlayerActorService.gd reads identity, inventory, combat, presentation, and movement through component lookups first, then packages those values into typed runtime and UI snapshots.

What The Shell Path Already Proves

  • ActorShell3D.gd is not empty scaffolding. It manages component collection, state-tag publishing, death-state toggles, and generic attack or hit-reaction relays.
  • engine3d/tests/smoke_actor_player_shell.gd verifies that ActorPlayerShell3D instantiates, exposes the component API, moves under shell-owned movement, synchronizes state across motor and presentation layers, and produces combat and inventory contracts.
  • The shell scenes therefore count as live migration assets, but not as universal runtime authority for every actor family.

Known Boundaries And Risks

  • ActorCharacter3D.gd remains the highest-risk actor file because player and NPC behavior still fan out from it.
  • The player path is hybrid: production still depends on the legacy root, while services and tests already exercise shell-style contracts.
  • Creature and animal coverage has not crossed over to a dedicated shell-root family in the current repo snapshot.

Validation

  • AGENTS.md explicitly documents ActorCharacter3D as the current runtime authority and the shell path as the migration target.
  • docs/production_rewrite_worklog.md records the actor-shell/component architecture as an active rewrite objective rather than completed migration.
  • engine3d/tests/smoke_actor_player_shell.gd is the strongest repo-native proof that the shell player scene owns real runtime behavior already.
