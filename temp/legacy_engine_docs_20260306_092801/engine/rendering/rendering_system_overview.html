Rendering System Overview

Purpose

This page documents the current rendering-system direction for the Densetsu engine: compatibility-first rendering, project-owned shader systems where needed, and preservation of debugging/troubleshooting knowledge from real integration failures.

Current rendering focus areas

  • Post-process outline pipeline (Sobel-based) for stylized edge detection.
  • Toon rendering controls and global parameter coordination.
  • Sky/weather rendering system with clock/calendar coupling and layered visuals.
  • Terrain3D integration sanity, persistence issues, and rendering consistency.
  • Shader compatibility assessment and replacement planning for unstable third-party shaders.

Core engineering principles

  • Compatibility first: avoid exotic setups that break common materials or produce render-device spam.
  • Sobel-first strategy: build the stylized outline stack around a working depth/normal screen pass that already matches project needs.
  • Project-owned replacements when necessary: replace incompatible third-party shaders with internal equivalents rather than forcing fragile workarounds.
  • Global vs local separation: global rendering controls should not unintentionally overwrite material-local authoring unless explicitly designed to do so.
  • Debuggability: expose parameters at top-level control nodes and preserve troubleshooting notes.

Why replacements are part of the rendering strategy

Outline/post-process integration exposed compatibility problems with several shaders and setups. In practice, the cost of preserving fragile third-party shaders can exceed the cost of replacing them with simpler, project-compatible variants. This is especially true when the project depends on a stable Sobel outline pass and consistent behavior across many materials/scenes.

System boundaries

  • Rendering category: shaders, post-process, sky/weather visuals, rendering performance behavior.
  • Integrations category: third-party plugin behavior, Terrain3D adaptation policy, compatibility notes.
  • Runtime category: boot/loading sequencing and non-render startup logic.

Some pages (especially sky/weather) cross runtime and rendering concerns; the implementation and visual behavior are documented here first, with runtime orchestration cross-linked elsewhere.

Known pain points (captured intentionally)

  • Shader compilation issues causing magenta/full-fail outputs.
  • Runtime-only post-process behavior being mistaken for editor-preview failure.
  • Parameters appearing to do nothing due to pipeline state, debug modes, or incorrect node bindings.
  • Cloud UV seams and rendering consistency problems in the sky system.
  • Terrain rendering consistency/persistence edge cases.
  • Driver/editor stability interactions during rendering-heavy workflows.

Documentation policy for this category

  • Document both working paths and failed experiments that produced useful lessons.
  • Separate current implementation from future plans clearly.
  • Prefer reproducible troubleshooting steps over vague advice.
  • Do not publish non-public game art/content details unless sanitized.
